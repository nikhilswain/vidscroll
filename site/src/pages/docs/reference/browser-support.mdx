Scroll-driven video itself works in every current browser. What varies is
whether a slow-to-scrub video can be fixed on the spot.

## What each feature needs

<Table>
  <thead>
    <tr><th>Feature</th><th>Needs</th><th>Without it</th></tr>
  </thead>
  <tbody>
    <tr><td>Scrubbing, pinning, sections</td><td>The <code>video</code> element and CSS <code>position: sticky</code></td><td>Available in all current browsers</td></tr>
    <tr><td>In-browser re-encoding</td><td>WebCodecs (<code>VideoDecoder</code> and <code>VideoEncoder</code>)</td><td>The original file is used; scrubbing is as smooth as the file allows</td></tr>
    <tr><td>Caching the re-encoded copy</td><td>Cache Storage</td><td>The re-encode runs on every visit</td></tr>
    <tr><td>Re-encoding and caching</td><td>A secure page: HTTPS or <code>localhost</code></td><td>Both are off, so plain-HTTP pages behave like browsers without WebCodecs</td></tr>
  </tbody>
</Table>

A video prepared with `npx vidscroll encode` needs none of the optional
features, which is why preparing files is the most reliable setup.

<Callout kind="warning" title="Safari and iOS">
  vidscroll hasn't been tested on real Safari or iOS devices yet. Prepared
  videos use only standard video playback and are expected to work; the
  in-browser re-encode depends on Safari's WebCodecs support. If you test it,
  please report what you find on GitHub.
</Callout>

## Other details

- **Firefox** may refuse to re-encode more than one video at the same time on
  a page; the others keep their originals.
- **Android browsers** use forward playback when scrolling forward, which is
  smoother there than seeking.
- **Low Power Mode** and similar settings that block video playback make
  vidscroll fall back to seeking for every frame.
- **Older browsers** without `svh` units use `vh` for the stage height.
