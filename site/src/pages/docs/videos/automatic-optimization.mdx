You can give `ScrollVideo` any MP4 or WebM, including one exported straight
from an editor. If its keyframes are too far apart for smooth scrubbing
([why that matters](/docs/videos/why-seeking-stutters/)), vidscroll fixes the
file in the visitor's browser. This is on by default.

## What visitors see

While the re-encode runs, the **original video is already on screen** and can
be scrolled. Scrolling forward plays it smoothly; scrolling backward is choppy
until the new copy arrives. A small badge in the corner shows the progress.
When the copy is ready, it takes over at exactly the frame on screen, so the
switch isn't visible.

In our tests, a 60-second 1080p clip took about 8 to 10 seconds to re-encode on
a desktop computer and about 20 seconds on an Android phone. Shorter clips are
proportionally faster.

To keep the loading overlay up until the smooth copy is ready instead, use
`wait`:

```tsx title="Hero.tsx"
<ScrollVideo src="/videos/hero.mp4" optimize={{ wait: true }} />
```

The browser encoder favours speed over size: for the clip above, the copy it
made was 18.6 MB, where the CLI produces 11.9 MB at the same resolution. That
file lives only in the visitor's browser, but it's one more reason to
[prepare videos ahead of time](/docs/videos/cli/) for production.

## Caching

The optimized copy is saved in the browser's Cache Storage, so later visits
load it straight away without downloading or re-encoding again. The cache entry
is tied to:

- the video's URL,
- the optimization settings, so changing `maxResolution`, `maxFps` or
  `maxKeyframeGap` creates a new copy,
- the file's identity, read from its `ETag`, `Last-Modified` or
  `Content-Length` header, so replacing the file on the server starts over.

<Callout kind="warning" title="No cache without those headers">
  If the server sends none of `ETag`, `Last-Modified` and `Content-Length`,
  vidscroll can't tell whether the file changed, so it doesn't cache it and
  the re-encode runs on every visit. Most hosts and CDNs send them.
</Callout>

Caching also needs a secure page (HTTPS or `localhost`), like WebCodecs itself.

## Options

Pass an object to `optimize` to change the defaults, or `false` to turn
optimization off:

```tsx title="Hero.tsx"
<ScrollVideo src="/videos/hero.mp4" optimize={{ maxResolution: 1080, cache: true }} />
```

## When to rely on it

Automatic optimization is ideal while building, for content that changes
often, and for videos you don't control. For a production page with a fixed
video, [pre-encode it with the CLI](/docs/videos/cli/): the file is smaller,
every visitor gets smooth scrubbing on their first visit, and phones skip the
work entirely.
